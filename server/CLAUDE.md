# server

Code that runs in Node, never in the browser: inside the Vite dev server (loaded from `vite.config.ts`), and the AI bridge, a small program that serves only the LLM endpoint on the player's computer for the published demo (`npm run bridge`, the bundled file `dist-bridge/ai-bridge.mjs` run with plain `node`, or `npx <site>/ai-bridge.tgz`).

| File               | Role                                                                                                                                                                                                                                                                                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `aiAccess.ts`      | Guard for `/api/*` (D37), the middleware `aiAccess(env, options)` used by the dev server (`aiAccessPlugin`) and the bridge: CORS for the online demo's origin; requests that do not come from localhost (i.e. through a tunnel) need `AI_PASSWORD` in the `x-ai-key` header. Requests that carry another website's `Origin` are refused (403) even on localhost: any page open in the browser can send a simple POST there. Refusals carry `x-ai-access: denied` and `Connection: close`: the request's body is not read, and its connection is closed after the answer (destroyed 1 s later if the other side goes on sending) instead of staying open until Node's own timeouts. |
| `llmEndpoint.ts`   | `POST /api/llm` (`llmEndpoint(env, { query, codex, server })` → `{ handle, close, ways }`), mounted by the dev server and the bridge: one persistent session per side (D10, D22). A new `matchId` or model starts a new session. The system prompt and the model (`haiku` / `sonnet` / `opus`, chosen per side in the menu, D29) come with each request; a Claude alias runs a `ClaudeSession` with the Agent SDK's `query` it is given (or answers the text it is given instead, 500 not retryable), `codex[:<model>]` a `CodexSession` with the Codex CLI installed on the computer, `gemini:<model>` a `GeminiSession`, `openrouter:<id>` and `local:<name>` a `ChatSession`, `cli:<name>` a `CliSession`. A model that cannot run here gets 500 not retryable saying why (an unknown `cli:` name 400). `ways()` says whether Codex and Gemini can run and lists the commands, for the bridge's status. `server` names the program in messages that say what to restart. |
| `llmPlugin.ts`     | The dev server's `/api/llm`: the Vite plugin that mounts `llmEndpoint` (`devLlmEndpoint`: with the Agent SDK it imports) at `/api/llm`, and (`llmStatusPlugin`, sharing that endpoint; mounted after the guard in `vite.config.ts`) `GET /api/bridge`: what it runs, in the AI bridge's status shape with `bridge: false`, for Match setup on the page it serves (`src/ai/ServerStatus.ts`); GET only (405), `/api/bridge/<more>` 404, a query allowed, `Cache-Control: no-store`, nosniff; behind the access guard as every `/api/` path (a tunnel needs `AI_PASSWORD`); never a secret. `llmPlugin` itself still mounts one handler. |
| `llmSession.ts`    | What every session kind shares (`LlmSession`, `Answer`, `LlmError`), in its own file so the endpoint and the session files do not import each other. |
| `claudeSession.ts` | `ClaudeSession`: a persistent, lean Claude Agent SDK session (the SDK's `query` passed in); each alias runs a pinned model id of the 5.5 generation (`MODEL_IDS`, D44), never the CLI's own alias. |
| `chatSession.ts`   | `ChatSession`: a model behind an OpenAI-compatible chat API, OpenRouter (D52) or a local server; what differs between the two is in `ChatApi` (`openRouterProvider`, `localProvider`). `localServer` reads `LOCAL_LLM_URL` (chat address, model list, origin) for both the provider and the bridge's status. Also what the other sessions share with it: `withoutThinking`, `capped` (300 characters), `MAX_ANSWER_CHARS`, `keyProblem`. |
| `codexSession.ts`  | `CodexSession`: OpenAI's Codex through the Codex CLI installed on the computer, one Codex session per side and match (below); `codexArgs` (the command line of a run), `readEvents` (its JSON Lines), `codexRunner` (whether it can run here: `codex` on PATH or `CODEX_PATH`, found without running it; the keys set on purpose), `codexMissing`. |
| `geminiSession.ts` | `GeminiSession`: Gemini through the Gemini API's Interactions API with `GEMINI_API_KEY`, one conversation per side and match chained by `previous_interaction_id` (below); `geminiProvider`. |
| `cliTools.ts`      | Commands of the server's own settings (`CLI_TOOL_<NAME>`, model `cli:<name>`): reading the settings (`cliConfig`, `splitCommand` without a shell), finding an executable without running it (`locate`), the status list (`cliStatus`), the small environment a started program gets (`passedOnEnv`, also used for Codex), colour codes removed. |
| `cliSession.ts`    | `CliSession`: such a command run once per report (below); `runProcess` (one program started for one report: no shell, its own process group, stdin, output caps, timeout), also Codex's. |
| `bridge.ts`        | The AI bridge (`startBridge`): a plain Node HTTP server on `127.0.0.1` only, serving `POST /api/llm` (the same `llmEndpoint`), `GET /api/bridge` (status; its `llm` from `llmStatus`, which the dev server's status shares) and a 404 for `/api/jev` and `/api/snap`; its settings (`loadSettings`), the local server's model list (`listLocalModels`), the demo link. |
| `bridgeCli.ts`     | The bridge's command: options (`--port`, `--no-open`), settings, loading the Agent SDK when it is there, the startup report, opening the demo connected to the bridge (`openBrowser`); the entry point of the bundle. |
| `bridgeClaude.ts`  | Claude on the bridge through the Agent SDK (2026-11-22, the author's decision): on the Claude Code sign-in of the person running the bridge, or with `ANTHROPIC_API_KEY` when it is set (the key into the Claude Code process's environment, the credentials ranked above it and the claude.ai token out of it); the bridge's other keys never in that environment. `claudeWay` for the status and the startup report. |

The decision-model proxies are configured directly in `vite.config.ts`: `/api/jev` (TypeSafe, `TYPESAFE_API_KEY`) and `/api/snap` (SubQ Snap, `SUBQ_API_KEY`, D51) both go to `/v1/systemone` and add their key from `.env.local` (D7, P1). They forward only `Content-Type`, `Content-Length`/`Transfer-Encoding`, `Accept` and the server's own `Authorization`: the browser's `Origin`, the AI password (`x-ai-key`), cookies, the referrer and any `Authorization` from the browser stay on the dev server. The allowlist is applied to the incoming request's headers on the proxy's `start` event, before they are copied (the proxy skips its `proxyReq` event for a request with an `Expect` header), and checked again on `proxyReq`. Only POST is proxied: another method gets 405 (the `decision-proxy-methods` plugin, after the guard). The service's `Set-Cookie`, `Access-Control-*`, `Location` and `Vary` headers are not passed back, so the guard's CORS headers are the ones the browser sees, and a redirect from the service becomes 502. A service that has not answered after `JEV_PROXY_TIMEOUT_MS` (14 s, `src/ai/Limits.ts`; `api/jev.ts` keeps the same literal) gets 504 and its request is closed, an answer whose body stalls is cut at that time, and an unreachable service gets 502: the browser retries these within its 30 s.

A model `openrouter:<id>` (D52) runs that model through OpenRouter's chat API with `OPENROUTER_API_KEY`: the session keeps the match's messages and sends them all with each request; HTTP 400–404 (wrong key, no credits, unknown model) are not retryable; cost comes from OpenRouter's `usage.cost`. An unknown model name is refused with 400. Both chat APIs (`ChatSession`) never follow a redirect: a 3xx is an error, not retryable (the rulebook and the report would go to whatever address it names). The service's own error text is cut to 300 characters in messages and the log. A key (`OPENROUTER_API_KEY`, `LOCAL_LLM_KEY`) is trimmed, and one with anything but printable ASCII (a line break, a pasted curly quote) is answered with 500, not retryable, before anything is sent: fetch would refuse it with an error that holds the whole header; the key is masked in fetch's own error text anyway. A session closed (new match or model) while an answer is read fails that request with "session was closed".

A model `local:<name>` runs `<name>` on the user's own computer (Ollama, LM Studio, llama.cpp) or any other OpenAI-compatible chat API. `LOCAL_LLM_URL` is the API's base, `<base>/chat/completions` is called (default Ollama's `http://localhost:11434/v1`; an address that already ends in `/chat/completions` is used as it is; http or https only; spaces around it, or only spaces, ignored), `LOCAL_LLM_KEY` an optional Bearer key (only spaces: none), `LOCAL_LLM_HISTORY_TURNS` how many earlier reports and answers each request carries again besides the rulebook and the new report (a plain whole number, default 3, `0` none: a local model's context window is small), with `stream: false`. The settings are read once when the dev server starts, from `.env.local` only, never from a request: the endpoint is reachable through the tunnel. The model name (checked in `Models.ts`) goes into the request's body and into the server's messages and log, never into the address. At start the log warns once about a `LOCAL_LLM_HISTORY_TURNS` that is not a whole number (3 is used) and about a key that would go over plain `http://` to another computer. A wrong `LOCAL_LLM_URL` (not http(s), a user name or password in it) or key is answered with 500, not retryable, saying what to fix. The answer: a reasoning model's thinking (`<think>` or `<thinking>`, any case, attributes) is removed: the answer is what follows the last closing tag, unless that has no `{` (an answer that only mentions the tag keeps its text); an opening tag that is never closed is dropped alone (`LlmReply` reads the JSON from the text's first `{`, which may be in the thinking). Content in parts is joined. An answer that is empty (a reasoning model may have used its whole output on thinking), cut off (`finish_reason: "length"`) or over 200 KB of text is an error that may pass, never a 200, and is not sent again: the browser would read it as no orders and go on, while failures are counted and three in a row stop the layer. OpenRouter's answers are taken as they come. Cost comes from `usage.cost` when the server sends a number (a paid API might) and counts towards `LLM_MAX_BUDGET_USD` as for OpenRouter; Ollama sends none, so no cost and no budget stop. Tokens from `usage` when the server sends them. Errors say what to do: the server unreachable (retryable; is it running, `LOCAL_LLM_URL`), 404 or a missing model (the server does not know the model, with Ollama `ollama pull <name>`, or `LOCAL_LLM_URL` is not its OpenAI-compatible address), 401/403 (`LOCAL_LLM_KEY`), a redirect (set `LOCAL_LLM_URL` to the final address); as for OpenRouter, 400–404 are not retryable.

A model `codex` or `codex:<model>` runs OpenAI's Codex through the Codex CLI installed on the computer (`CODEX_PATH`, else `codex` on PATH, found without running it), driven as OpenAI's TypeScript SDK drives it, without the SDK (2026-11-22: the SDK carries its own ~400 MB Codex, which kept Codex out of the bridge's one command). Sources, read 2026-11-22: [non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode.md), the [config reference](https://learn.chatgpt.com/docs/config-file/config-reference.md), and on GitHub `openai/codex`: `codex-rs/exec/src/cli.rs`, `lib.rs`, `exec_events.rs`, the SDK's `sdk/typescript/src/exec.ts` and `thread.ts`. A session per side and match, as Claude's: the first report runs `codex exec --json <settings> [--model <name>] --sandbox read-only --cd <empty folder> --skip-git-repo-check --ignore-user-config --ignore-rules -` (the report on stdin), every later one the same with `resume <id> -`, the id from the first run's `thread.started` (an id that could be read as an option is never passed on), so Codex keeps the conversation (its session files in `CODEX_HOME`) and only the new report is sent. Settings (`--config key=value`, TOML values as the SDK writes them): `model_instructions_file` = the rulebook (a file beside the empty working folder; it replaces Codex's own instructions), `features.shell_tool`, `view_image`, `apps`, `multi_agent`, `remote_plugin`, `hooks` false, `skills.bundled.enabled` false, `mcp_servers={}`, `web_search="disabled"`, `approval_policy="never"`, `sandbox_workspace_write.network_access=false`; `--ignore-user-config` skips `$CODEX_HOME/config.toml` (the sign-in still comes from `CODEX_HOME`), `--ignore-rules` the execpolicy rules. Not `--ephemeral`: it keeps no session files, and `resume` in the next process reads them, so Codex's sessions stay on disk. Not locked down: what an administrator manages (`requirements.toml`, managed hooks), plugins the user installed (their own MCP servers and skills; `plugins._default.enabled` is not set), what the read-only sandbox lets the model read. Started without a shell (arguments as an array) in its own process group (`runProcess`: 110 s, a new match or the server closing stop it and what it started); its environment is `passedOnEnv`'s with `CODEX_HOME`, `CODEX_SQLITE_HOME`, `CODEX_CA_CERTIFICATE`, and `CODEX_API_KEY` / `OPENAI_API_KEY` only when set in the settings on purpose (masked in Codex's messages). The answer is the turn's last `agent_message`; events that end before `turn.completed` (cut off), an empty answer or one over 200 KB are errors that may pass, never a 200. Errors come from `turn.failed`, an `error` event, or the end of stderr, cut to 300 characters: not signed in (401, `codex login`), a limit of its plan or key, a model it cannot use, a command line or settings this Codex refuses (another version), a sandbox that cannot run here: not retryable; a sandbox refusal, a broken stream and the rest may pass. A session Codex no longer has (`resume` fails, "no rollout found for thread id <id>") is started again at once with the report (once, logged). Tokens from `turn.completed`'s `usage`; no cost. Windows: without a shell only a `codex.exe` can be started (the standalone installer's), not npm's `codex.cmd`; `CODEX_PATH` can name a `codex.exe`.

A model `gemini:<model>` runs Gemini through the Gemini API's [Interactions API](https://aistudio.google.com/docs/interactions-overview) with `GEMINI_API_KEY` (as `x-goog-api-key`; a key a header cannot carry refused before anything is sent; masked in fetch's own error text). `POST https://generativelanguage.googleapis.com/v1/interactions` (the stable v1 of `interactions-v1.openapi.json`; the overview's examples use `v1beta`), a constant: never from a request, redirects not followed. A session per side and match: Google keeps the conversation (`store`, the default) and each report continues it with `previous_interaction_id`, so only the new report is sent; the rulebook goes as `system_instruction` with every request, because the API keeps "only the conversation history (inputs and outputs)" and system instruction, tools and generation config "must be re-specified in each new interaction". Google retains stored interactions 55 days (paid tier) or 1 day (free tier). A conversation that is lost (a 404, or a 400 naming the previous interaction, while continuing) is started again at once with the report at hand (one more call, logged). The answer: the text parts of the `model_output` steps (thoughts left out); status `incomplete` (cut off), `failed` and others are errors that may pass, as are an empty or oversized answer; 400–404 not retryable (401/403: check the key; 404: the model), 429 may pass (a rate limit or quota). Tokens from `usage` (`total_input_tokens`, `total_output_tokens`, `total_cached_tokens`); no cost. The Gemini CLI is not used: its documentation forbids using its sign-in from third-party software and it stopped serving unpaid and Google One accounts on 2026-06-18 ([geminicli.com/docs/resources/tos-privacy](https://geminicli.com/docs/resources/tos-privacy)).

A model `cli:<name>` runs a command of the server's own settings, `CLI_TOOL_<NAME>=<executable and arguments>` (the environment or `.env.local`; `<name>` is `<NAME>` in lower case), never from a request: a request only names one, and a name the settings do not have is an unknown model (400). The command is split without a shell (quotes and backslashes keep words together; no variables, `~`, pipes or globs) and run as written, once per report (stateless): the rulebook, the last `CLI_HISTORY_TURNS` (default 3, same rules as `LOCAL_LLM_HISTORY_TURNS`) reports and answers and the new report as one plain-text prompt on stdin (`=== RULES ===`, `=== EARLIER REPORT k ===` / `=== YOUR ANSWER TO EARLIER REPORT k ===`, `=== NEW REPORT ===`, "Answer the new report."), its whole stdout the answer (colour codes and thinking removed; empty or over 200 KB an error that may pass). The server does not lock a command down: it runs what the setting says. It runs in an empty folder of its own (removed when the session closes) with the small environment of `passedOnEnv` (none of the server's keys), as the leader of its own process group: a timeout (the endpoint's 110 s), a new match or the server closing stops the group (SIGTERM, SIGKILL after 1.5 s), and what it leaves running after it answered is ended too. Output read up to 4 MB (more: stopped, an error), the last 64 KB of stderr kept; a failure shows the end of its stderr (300 characters; a refused command line, not retryable). The executable is found without running it (absolute PATH folders only; on Windows only `.exe`/`.com`: no shell, so no `.cmd`). `CLI_TOOLS=off` turns them off (500 not retryable). Not in the README's main path; earlier presets for Claude Code, Codex CLI and Gemini CLI (2026-11-22) were replaced by the sessions above.

## Conventions

- Uses the developer's own Claude login (personal, local use; D9, D10). Final experiments switch to the Claude API.
- Keep sessions lean: custom system prompt, no tools, no project settings, auto memory off. The default Claude Code setup makes the model answer as a coding assistant (R2).
- The system prompt defines the reply format; the browser validates every reply anyway.
- Not part of `npm run build`: the static build has no `/api/*` endpoints. The online demo reaches them through a tunnel to the author's computer (D37); `vite.config.ts` allows the tunnel host names (`allowedHosts`). Or through the AI bridge on the player's own computer (below).
- `aiAccess` must stay the first plugin, so its check runs before the Jev proxy and the LLM endpoint.
- `/api/llm` is reachable through the tunnel, so it is bounded: bodies over 1 MB (counted in bytes, refused at once when Content-Length says so) get 413 and a body that stalls for 30 s gets 408, the answer sent before the connection is closed; `side` must be `west` or `east` (one session each), a body that is not JSON or whose `side`, `matchId`, `system` and `prompt` are not text gets 400, and an answer that has not come after 110 s (below the browser's 120 s) fails with the session closed (the next request opens a fresh one). A session that is closed (new match or model) or whose SDK stream ends fails its waiting requests at once, and an ended session is replaced by the next request.
- An SDK result with `is_error` (an API error after the CLI's own retries, e.g. overloaded, rate limited, a plan limit, an expired login) or an error subtype is an error, never the model's reply. It is answered with 500, `{ error, retryable }`: plan, budget and login problems are not retryable. Such an error leaves the session open, so the match keeps its conversation.
- The dev server's output logs, per side, the model each session actually runs, every retry the Claude CLI makes on its own (status, delay) and each answer's time, and every failed request; nothing secret is logged.
- Each answer carries what it cost: `costUsd` (this answer: from the SDK's running total, or a chat API's `usage.cost`; null when the service reports none, as a local server usually does), input, output and cached tokens, `apiMs` and the full `modelIds` (estimates, for Q11). A session stops at `LLM_MAX_BUDGET_USD` (default 5) of estimated spend; a service that reports no cost never reaches it.
- `LLM_MODEL`, `LLM_MAX_BUDGET_USD`, `OPENROUTER_API_KEY`, `LOCAL_LLM_URL` / `LOCAL_LLM_KEY` / `LOCAL_LLM_HISTORY_TURNS`, `GEMINI_API_KEY`, `CODEX_API_KEY` / `OPENAI_API_KEY` / `CODEX_PATH`, `CLI_TOOL_<NAME>` / `CLI_HISTORY_TURNS` / `CLI_TOOLS` are read from the `env` Vite loads (passed to `llmPlugin(env)`): `.env.local` and the shell's environment, a shell export winning over the file for the same variable (Vite's `loadEnv` with the prefix `''` copies `process.env` over the parsed files), and `process.env` again when `env` has none.
- `/api/llm` reads at most 8 request bodies at once (more get 503 with `Retry-After: 5`); a browser that closes its request is not waited for (the session and its conversation stay, the late answer is dropped); two matches alternating on one side are logged, at most once a minute per side.

## The AI bridge

- Why: the published demo (static, GitHub Pages) has no `/api/*`; the bridge lets a player use their own model with it without running the dev server. The page connects to it from the title screen's This computer card (Connect) or Match setup's Connect… (`src/ai/BridgeConnect.ts`, `src/ui/Connections.ts`): a click asks `GET /api/bridge` at `http://127.0.0.1:8642`, or at the bridge the page already knows (`?ai=http://127.0.0.1:<port>`, the link the bridge prints, or one connected before), with Local Network Access's `targetAddressSpace: 'loopback'`; reached, the bridge becomes the page's AI server and its LLM requests go there with the same option. Nothing calls the bridge at page load. The menu lists what the status says it runs (local models, Claude, Codex, Gemini, OpenRouter on its key, its commands) and, disabled with why, what it cannot; Start refuses what the bridge cannot run (see `src/ui/CLAUDE.md`). On the published page OpenRouter is the main way and the bridge one quiet line ("Or use your own computer: Ollama, Claude Code, Codex") until a bridge is in play; its dialog has the one command with a Copy button, what it finds (Ollama or another local model server, Claude Code, Codex), the browser's question the first time and an optional line for Gemini (`GEMINI_API_KEY` in `.env.local`). The bridge opens the demo with its own address (`?ai=`): a page that comes with a bridge's address connects it at load when the browser's permission is granted or the browser has no such permission, and otherwise invites the one click that lets it ask (`src/ai/BridgeConnect.ts`, `connectAtLoad`). Default port `DEFAULT_BRIDGE_PORT` (8642, not Vite's 5173/5174), shared with the page from `src/ai/Limits.ts`; `--port <n>` or `BRIDGE_PORT` (0: any free port).
- It exposes the player's model and keys to web pages, so: it listens on `127.0.0.1` only (no option to listen elsewhere: any other option is refused); a request whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` with the bridge's port is refused with 403 before anything else (DNS rebinding); the guard is `aiAccess` with `loopbackOrigins` (pages on this computer, `localhost` / `127.0.0.1` / `[::1]` on any port, as a well-formed origin, may call like the allowed sites); no Private Network Access answer (`Access-Control-Allow-Private-Network`): Chrome's Local Network Access (a permission the user grants, Chrome 142) replaced it, its preflights were never enforced, and Chrome's guide says not to add it to new code; another site's `Origin`, `null` included, gets 403; a request without `Origin` (a program on this computer) passes, as on the dev server; every answer has `X-Content-Type-Options: nosniff`. No AI password: every request it answers is addressed to this computer. Do not put it behind a tunnel: that is what the dev server with `AI_PASSWORD` is for.
- Paths are exact (`/api/llm`, `/api/bridge`, `/api/jev`, `/api/snap`, a query allowed); anything else is 404. `/api/llm` behaves as on the dev server (same limits: 1 MB, 30 s body, 8 bodies at once, 110 s answer). `GET /api/bridge` (GET only, `Cache-Control: no-store`; `version` 1.1.0 since 2026-11-22): `{ bridge: true, version, llm: { claude, codex: { available, reason? }, gemini, local: { url, models }, openrouter, custom: [{ id, label, available }] } }`; `claude` true when the Agent SDK loads (and a set `ANTHROPIC_API_KEY` can be sent), `codex.available` when the Codex CLI is found (`CODEX_PATH` or `codex` on PATH, nothing run; `reason` says what to do otherwise: install it and sign in, fix `CODEX_PATH`, a key that cannot be sent), `gemini` when `GEMINI_API_KEY` is set and can be sent, `custom` the `CLI_TOOL_<NAME>` commands (`cli:<name>`, "<name> (this computer)", the executable found; empty with `CLI_TOOLS=off`); `url` is `LOCAL_LLM_URL`'s origin only (null when it cannot work), `models` the ids of the local server's OpenAI-compatible `GET <base>/models` (with `LOCAL_LLM_KEY` as Bearer when set; 2 s timeout, redirects not followed, at most 1 MB, names a model id may have, once each, at most 200), null when it does not answer that way; booleans for the keys, never a key, a path or a command.
- `/api/jev` and `/api/snap` (the decision models) are not served: their keys are the author's (D7) and the dev server's proxies are Vite's (http-proxy), so sharing them would mean a second proxy. POST gets 404 `{ error }` saying to choose "LLM" for the side; the browser stops the tactical layer at once on a 404 and the LLM goes on alone. The menu does not let it come to that: AI + Jev / AI + Snap are refused at Start while the page's AI server is a bridge. Another method gets 405.
- Claude through the Agent SDK (`bridgeClaude.ts`; 2026-11-22, the author's decision: until then only with `ANTHROPIC_API_KEY`): without a key the Claude aliases run on the Claude Code sign-in of the person running the bridge, as the dev server runs on the author's (D9, D10); with `ANTHROPIC_API_KEY` (environment or `.env.local`) the key goes into the Claude Code process's environment and `CLAUDE_CODE_USE_BEDROCK` / `_VERTEX` / `_FOUNDRY`, `ANTHROPIC_AUTH_TOKEN` (ranked above the key) and `CLAUDE_CODE_OAUTH_TOKEN` (a claude.ai token) are removed from it. The bridge's other keys (`OPENROUTER_API_KEY`, `LOCAL_LLM_KEY`, `GEMINI_API_KEY`, `CODEX_API_KEY`, `OPENAI_API_KEY`, and the project's `TYPESAFE_API_KEY`, `SUBQ_API_KEY`, `AI_PASSWORD`) never reach it. Not signed in: the SDK's own error comes through as on the dev server (not retryable). Anthropic's documentation says third-party developers may not offer claude.ai login for their products without approval and asks for API key authentication (Agent SDK overview; [legal and compliance](https://code.claude.com/docs/en/legal-and-compliance.md)); the README says that using one's own sign-in through the bridge is the player's judgement and an API key the documented way. Without the SDK the Claude models are off (500 not retryable saying how to get it; `claude: false`).
- The Agent SDK is not bundled (it starts Claude Code's own program): the bundle imports it at run time from `node_modules` next to the file (a clone's, for `npm run bridge`; npx's, for the packed bridge, whose `package.json` declares `@anthropic-ai/claude-agent-sdk` as its only dependency at the repository's range; `scripts/pack-bridge.mjs`). Without it only the Claude models are off. Codex needs no package: the Codex CLI installed on the computer runs it, so the one command covers Ollama, Claude Code and Codex. The SDK's native Claude Code program is most of the download (2026-11-22, darwin-arm64: 409 MB installed by npx, of it ~364 MB the program; with npm's `--omit=optional` 62 MB). Using the installed `claude` instead (`pathToClaudeCodeExecutable`) was looked at and not done: a dependency cannot omit its own dependency's optional package (only the user's command or the root project can: `npx --omit=optional …`), the SDK pins one Claude Code version (`claudeCodeVersion`) the installed one may not match, and a visitor without Claude Code would lose Claude.
- Settings (`SETTINGS`): `LOCAL_LLM_URL`, `LOCAL_LLM_KEY`, `LOCAL_LLM_HISTORY_TURNS`, `LLM_MODEL`, `LLM_MAX_BUDGET_USD`, `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `CODEX_API_KEY`, `OPENAI_API_KEY`, `CODEX_PATH`, `AI_ALLOWED_ORIGINS`, `BRIDGE_PORT`, `BRIDGE_OPEN`, `CLI_TOOLS`, `CLI_HISTORY_TURNS` and any `CLI_TOOL_<NAME>`, from the environment and `.env.local` in the working folder (Node's `util.parseEnv`), the environment winning as with the dev server; nothing else of `.env.local` is read (not the decision models' keys, not `AI_PASSWORD`). Messages that say what to restart name "the bridge".
- Startup output: the address, then a line per way: the local server's models (or that it does not answer), Claude (the Claude Code sign-in, the API key billed to its account, or off and why), Codex (found: the Codex sign-in, with `CODEX_API_KEY` when set; not found: "install it and sign in: npm install -g @openai/codex, then codex login"; off and why), Gemini and OpenRouter (key set, or optional), the commands of the settings (only when there are any, found or not), where the settings came from, the allowed sites. Then it opens the demo with this bridge (`DEMO_URL?ai=http://127.0.0.1:<port>`) in the default browser: macOS's `open`, `xdg-open`, or `cmd /d /c start "" <link>` on Windows (the link is the constant and a port number), found on PATH, started without a shell and detached, the bridge's keys out of its environment; only when the demo is an allowed origin; `--no-open` or `BRIDGE_OPEN=0`/`off` turn it off; it never stops the bridge ("Could not open a browser here."). The link is printed (for another browser), with "The first time, the browser asks whether the site may reach your computer: allow it." When `AI_ALLOWED_ORIGINS` leaves the demo out: how to add `?ai=` to the site instead. Never a key. A port in use or one that needs administrator rights is a one-line message and exit 1; a bad option or port exit 2.
- The page against the real bridge program (the bundle, a fake OpenAI-compatible server behind it) is tested in headless Chrome over http on 127.0.0.1 (`tests/smoke/bridge-chrome.sh`): connect, the model list, a match round. A page on 127.0.0.1 calling 127.0.0.1 is not a Local Network Access case, so that run shows no prompt.
